> 문서 버전: v1.0

# 1. 프로젝트 개요

## 1.1 서비스 정의

전국의 리폼·수선·복원 전문 업체를 사용자가 쉽고 정확하게 찾을 수 있도록 제공하는 **리폼 전문 검색 플랫폼**을 구축한다.

기존 포털/지도 검색이 단순히 업체명, 주소, 리뷰 중심이라면 본 플랫폼은 다음과 같은 **리폼 전문 데이터**를 중심으로 검색 경험을 제공한다.

- 품목
- 작업 종류
- 전문 분야
- 취급 브랜드
- 지역
- 택배 가능 여부
- 방문/출장 가능 여부
- Before / After 사례
- 작업 기간
- 가격 정보
- 포트폴리오
- 업체 인증 여부

초기에는 **정보 검색 서비스**로 시작한다.

시장성과 트래픽이 검증되면 동일한 플랫폼을 기반으로 다음 기능을 확장한다.

`업체 검색 → 문의 → 견적 → 중개 → 결제 → 정산 → 안심보상/보험`

# 2. 프로젝트 목표

## 2.1 1차 목표

초기 단계의 핵심 목표는 거래 중개가 아니라 다음 세 가지다.

### 사용자

사용자가 자신의 물건을 리폼·수선할 수 있는 업체를 쉽게 찾을 수 있어야 한다.

### 데이터

어떤 지역, 품목, 작업, 업체를 사용자가 많이 찾는지 데이터를 축적한다.

### 업체

플랫폼을 통해 업체가 실제 고객 유입 효과를 확인할 수 있는 기반을 만든다.

# 4. 서비스 핵심 컨셉

서비스는 크게 세 가지 경험으로 구성한다.

## 4.1 Find

조건에 맞는 리폼 업체를 검색한다.

예:

```text
서울
+
가방
+
가죽 염색
```

또는

```text
경기
+
소파
+
천갈이
```

---

## 4.2 Discover

Before / After 및 작업 사례를 통해 사용자가 어떤 리폼이 가능한지 발견한다.

예:

```text
기존 명품가방
→ 미니백 형태 변경

오래된 가죽소파
→ 가죽 교체

낡은 구두
→ 밑창 교체 및 복원
```

---

## 4.3 Match

사용자가 원하는 작업 유형에 적합한 업체를 찾는다.

향후에는 다음 단계까지 확장한다.

```text
사용자 사진 업로드

↓

품목/문제 선택

↓

가능한 작업 추천

↓

적합 업체 추천
```

# 5. 확정 기술 스택

## 5.1 Hosting

**Cafe24 뉴아우토반 비즈니스**

공유 웹호스팅 환경을 사용한다.

현재 카페24 뉴아우토반은 PHP 8.4, PHP 8.2, PHP 7.4 및 MariaDB/UTF-8 환경을 제공한다.

공유호스팅이므로 다음 제약을 전제로 설계한다.

- Root 권한 없음
- 상시 실행 프로세스 사용 불가
- 별도 데몬 설치 불가
- Cron 사용 불가
- Redis 서버 직접 운영 불가
- Queue Worker 상시 실행 불가
- 서버 설정 자유 변경 불가

카페24는 뉴아우토반 공유호스팅에서 Cron을 지원하지 않는다.

# 10. URL 구조

Cafe24 뉴아우토반 비즈니스에서는 서브도메인과 특정 폴더를 직접 매핑하는 기능을 제공하지 않으므로 API 전용 서브도메인을 전제로 설계하지 않는다.

따라서 초기 URL은 다음과 같이 구성한다.

```text
https://service.com/
```

```text
https://service.com/api/v1/
```

API

```text
https://service.com/admin/
```

관리자

예:

```text
GET https://service.com/api/v1/businesses
GET https://service.com/api/v1/businesses/123
POST https://service.com/api/v1/auth/login
```

# 13. 웹과 API 로직 공유

웹에서 자신의 API를 HTTP로 다시 호출하지 않는다.

예:

```text
WEB BusinessController
             │
             ▼
      BusinessService
             │
             ▼
     BusinessRepository
             │
             ▼
          MariaDB
```

API 역시 동일한 Service를 사용한다.

```text
API BusinessController
             │
             ▼
      BusinessService
             │
             ▼
     BusinessRepository
             │
             ▼
          MariaDB
```

이를 통해 웹과 앱에서 동일한 검색 결과와 비즈니스 정책을 사용할 수 있도록 한다.

# 18. 인증 방식

## 웹

PHP Session 기반 인증을 사용한다.

```text
ID/PW
↓
Session
↓
Secure Cookie
```

Cookie 기본 정책:

```text
HttpOnly = true
Secure = true
SameSite = Lax
```

---

## React Native

Bearer Token 인증을 사용한다.

JWT를 필수로 사용하지 않는다.

초기에는 DB에서 관리 가능한 **Opaque Access Token 방식**을 사용한다.

```text
로그인

↓

Access Token 발급

↓

React Native Secure Storage 저장

↓

Authorization: Bearer {token}
```

DB에는 실제 Token을 저장하지 않고 Token Hash를 저장한다.

# 24. 업체 DB Source 관리

각 업체 데이터에는 데이터 출처를 반드시 저장한다.

```text
source_type

source_url

collected_at

last_verified_at

claimed_by_owner
```

예:

```text
source_type = OFFICIAL_WEBSITE
source_url = https://...

source_type = PUBLIC_DATA

source_type = OWNER

source_type = MANUAL_RESEARCH
```

검색포털은 업체 후보를 발견하기 위한 도구로 사용할 수 있으나 포털의 리뷰, 사진, 소개문구 등을 그대로 복제하여 자체 DB 자산으로 만드는 구조는 사용하지 않는다.

최종적으로는:

```text
외부 발견
↓
업체 공식 출처 확인
↓
우리 DB 구축
↓
업체 Claim
↓
업체 직접 관리
```

구조로 전환한다.

# 41. 데이터베이스 개발 원칙

금지:

```php
$sql = "SELECT * FROM users WHERE id = " . $_GET['id'];
```

사용:

```php
$stmt = $pdo->prepare(
    'SELECT * FROM users WHERE id = :id'
);

$stmt->execute([
    'id' => $id
]);
```

# 75. 최종 방향

서비스의 최초 목표는 **“전국 리폼 업체를 찾을 수 있는 또 하나의 지도 서비스”가 아니다.**

최종적으로 다음 질문에 가장 잘 답하는 플랫폼을 목표로 한다.

> 내가 가진 물건을 어떻게 고칠 수 있는가?

> 어떤 리폼이 가능한가?

> 이 작업을 잘하는 업체는 어디인가?

> 실제로 비슷한 작업을 한 사례가 있는가?

초기 검색 데이터를 축적하면서 사용자가 실제로 원하는 Category, Service, Region, 업체를 파악하고 그 데이터를 기반으로 향후 견적·중개·거래 플랫폼으로 확장한다.
